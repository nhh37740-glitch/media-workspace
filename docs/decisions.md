# 设计决定记录

记录实现过程中做过的、需要解释的选择。每条都写清：背景、决定、被放弃的选项和理由。
规范里已经写明的决定不重复；这里只记规范没有指定、由实现补齐的部分。

---

## D-01 集成测试不用 Testcontainers，改用每次运行自建 schema

**背景**：05 号规范优先 Testcontainers，允许“明确隔离的 Compose 测试栈”。

**决定**：不用容器。`IntegrationEnvironment` 为每次运行生成 `mw_it_<随机>` 库名与独立存储目录，
用与生产相同的 Flyway 脚本迁移，测试结束删除该库。Kafka 的隔离靠主题前缀与消费组前缀。

**理由**：演示主机没有容器引擎，安装 Docker 需要额外的内核与存储配置，而规范允许隔离的本地服务。
建库而不是建容器同样满足“测试不接触演示数据”：库名按运行生成，且 `mw_it_%` 之外没有权限。

**代价**：不同运行共享同一个 broker，隔离强度弱于独立容器；因此消费组名也加了前缀，
避免运行之间的位点互相干扰。

## D-02 合并文件按“声明的全文件 hash”寻址，而不是按 epoch 目录

**背景**：04 号规范要求合并写“独立 epoch 路径”，并允许最终确定失败时置 FAILED。

**决定**：合并结果写在 `merge/{uploadId}/{expectedHash}/original.bin`。

**理由**：内容由分片唯一决定，而该键只在全文件 hash 校验通过后才会被写入，因此它是内容寻址的。
这带来两个规范想要的性质，而且更强：重复执行可以直接复用已有文件（规范要求“合并结果保留”），
而失效的 finalizer 写不出与声明不符的内容。epoch 仍然存在，并且仍然守着发布那一步 ——
数据库指针只有 epoch 匹配才能写入。

**代价**：同一上传若声明的 hash 不同（即请求体不同），会写两份文件；这是正确行为。

## D-03 租约与截止时间一律用数据库时钟判断

**背景**：04 号规范要求“DB CURRENT_TIMESTAMP(6) 判断，不能依赖 Worker 本机时钟”。

**决定**：端口层不再接收 `Instant` 参数，只接收 `Duration`；SQL 里所有比较用
`UTC_TIMESTAMP(6)`，`next_run_at` 也用 `DATE_ADD(UTC_TIMESTAMP(6), INTERVAL ? MICROSECOND)` 计算。

**理由**：把时钟来源收敛到一处，就不存在“某个调用点忘了改用数据库时钟”的可能。
Java 侧仍用 `Clock` 生成 `created_at` 之类的记录值，但那些值不参与任何判定。

## D-04 事务边界放在应用层，需要先做文件 IO 的步骤单独拆 Bean

**背景**：02 号规范要求“跨文件 I/O、网络发送和转码不放进长事务”，
同时要求“在单独 Bean 的 public 用例方法施加事务”。

**决定**：`UploadService.putChunk` 不开启事务，先把分片流式写入磁盘，再调用
`UploadChunkCommitService.commit`（独立 Bean，`@Transactional`）。同理，
`UploadFinalizeService` 做合并，`UploadFinalizeTransactionService` 做发布；
`TaskExecutionService.run` 做转码，`TaskPublicationService` 做落库。

**理由**：同一个类里的 `@Transactional` 私有/包内方法调用不会经过代理，事务根本不生效 ——
这一点不会报错，只会让数据在崩溃时不一致，所以必须用结构来避免。

**代价**：类变多了。这是为了让边界可以被静态地看出来。

## D-05 SSE 用 fetch 流而不是 EventSource

**背景**：03 号规范写明“SSE 使用 fetch 流”。

**决定**：`web/src/api/eventStream.js` 用 `fetch` + `ReadableStream` 解析 `id/event/data` 帧。

**理由**：规范如此要求，而且实际更好：`EventSource` 无法带 CSRF 头，且失败时只给一个不透明的
错误，无法区分“权限被撤销”和“网络断了”。用 fetch 能拿到真实状态码，并据此决定是重连还是停止。

## D-06 Worker 增加一个仅监听回环的 actuator 端口

**背景**：01 号规范说 Worker 没有公共业务端口；04 号规范又要求“存活与就绪分开，
DB 不可用 ready=false”，这对 Worker 同样适用。

**决定**：Worker 引入 `spring-boot-starter-web`，只监听 `127.0.0.1:8090`，只暴露 actuator。
不提供任何业务路由。

**理由**：没有端点就没有办法在不读日志的情况下判断 Worker 是否可用。回环绑定与“无公共业务端口”
并不冲突：它不对外，也不承载业务。

**代价**：Worker 多一个 Tomcat，多占约 40 MiB。实测总占用仍在预算内。

## D-07 演示环境的 Kafka 主题不加前缀

**背景**：`TopicNames` 支持给主题与消费组加前缀，用于隔离并行测试。

**决定**：演示环境的 `KAFKA_TOPIC_PREFIX` 为空，主题名与规范一致；前缀只在测试运行时使用。

**理由**：规范把主题名写成了契约的一部分（`media.task.requested.v1` 等）。
如果为了这个特性给演示环境加前缀，契约里的名字就与实际不符。
这个特性本来是为“同一个 broker 上跑多套隔离测试”准备的，那里它是必需的。

**教训**：前缀最初只在消费端应用，生产端写了不带前缀的名字，事件被 broker 接收但没人消费，
任务停在 WAITING_EVENT。现在前缀只在发送那一刻解析一次，并有测试锁定两端一致。

## D-08 构建与常驻服务错峰

**背景**：实测这台 2 GiB 的机器在“两个应用 JVM + MySQL + broker + Gradle 构建”同时运行时，
SSH 握手会超时 —— 机器在交换分区上抖动到无法调度。

**决定**：`deploy-demo.sh` 先停服务再构建；`ci-prepare.sh` 在 Jenkins 的构建阶段同样先停服务，
只保留 MySQL 与 Kafka（集成测试需要）。

**理由**：这类抖动不是“慢”，而是让主机不可用，连排查都做不到。停机窗口本来就要重启服务，
所以提前停止的额外代价接近零。

## D-09 分享会话存在服务端表里，cookie 只带一个不透明 id

**背景**：03 号规范要求“设置仅分享用途的 HttpOnly cookie”，并要求撤销立即生效。

**决定**：`share_session` 表保存 `(id, share_id, media_id, expires_at)`，
每次播放请求都重新读取对应的 `share_link` 并校验未撤销、未过期、素材未删除。

**理由**：如果 cookie 自身携带足够信息（例如签名过的 shareId），撤销就必须等到 cookie 过期或
引入吊销列表。每次多读一行是更小的代价，换来的是“撤销对新请求立即生效”这个可以直接断言的性质。

## D-10 提示性状态与权威状态分离

**背景**：01 号规范说“所有进度是提示；任务终态以 API 查询为准”。

**决定**：SSE 帧只用于让界面动起来；收到终态帧后前端会再 `GET /tasks/{id}` 确认。
Worker 的进度写库最多每秒一次（`ProgressReporter`），且值被夹在 0..99，
100 只能由发布事务写入。

**理由**：断线、重复、乱序都不能影响用户看到的结论。进度条短暂滞后是可以接受的，
把未完成的任务显示成完成不可以。
